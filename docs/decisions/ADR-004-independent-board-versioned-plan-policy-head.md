# ADR-004：使用不可变策略回执与 CAS head，而不原地修改套餐基线

## 状态

Accepted（W3h 本地候选）

## 日期

2026-07-22

## 背景

现有 `fbs_product_plan` 同时承担产品/套餐身份、初始能力基线和外键目标。`public_init_030` 会在每次重放时严格核验 `BOARD_FREE` 与 `BOARD_VIP` 的种子值。若管理后台直接 UPDATE 这两行：

- 旧初始化步骤的完成态重放会把合法业务修订误判为 schema 漂移；
- 只能看到最新值，无法可靠重建谁在何时把策略从什么版本改成什么版本；
- 读链可能在策略更新与审计写入之间观察到分裂状态；
- 修改身份行会扩大外键和既有权益的风险面。

## 决策

保留 `fbs_product_plan` 为不可改写的身份和基线层。新增：

- 只增不改的 `fbs_plan_policy_revision_receipt`，保存每次已提交策略的完整类型化快照、版本、前序摘要和操作者证据；
- 每个产品套餐一行的 `fbs_plan_policy_head`，通过版本和前序回执双条件 CAS 指向当前已提交回执。

所有当前读联接基线身份、head 和回执；写事务先锁定完整两套餐目录，验证跨套餐不变量，再插入回执并 CAS head。两个动作在同一 InnoDB 事务中提交。

## 备选方案

### 原地 UPDATE `fbs_product_plan` 并写普通审计日志

拒绝。它破坏旧迁移的可重放语义，且普通日志不足以成为可验证的策略真源。

### 只在修订表中按最大版本推导当前值

拒绝。并发写入和“哪条已经被激活”会依赖排序推断；显式 head 能提供唯一当前指针和清晰 CAS。

### 每次修订复制整张产品配置

拒绝。当前只有两个稳定套餐身份，复制产品和权限配置会制造多版本身份分叉，而非单一版本化策略。

## 后果

- 增加两张表、不可变触发器和更严格的迁移/真库验证成本；
- 策略写入按产品串行锁定两个 head，吞吐较低但治理操作频率低，换取确定性跨套餐不变量和无死锁锁序；
- 旧应用回滚后仍可读取原基线，新增表为纯加法；新应用部署必须先完成 039 迁移；
- 回执可支持后续策略差异展示、审批流和签名链，但本波次不自动晋级生产、不增加审批绕过或租户管理员。
