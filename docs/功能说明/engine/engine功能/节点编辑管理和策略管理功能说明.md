## 源码校准说明（2026-07-10）

以下内容以当前实现为准：

1. 节点编辑与策略页面实际位于 `WxFbsir-ui/src/views/business/content/NodeEditWithStrategy/`。
2. 当前页面以 WebSocket 发送 `YUANQI_EDIT_NODE`，成功后再发送 `YUANQI_PUBLISH_WORKFLOW`；`YUANQI_DEBUG_WORKFLOW` 是 Engine 已注册能力，未由该页面直接触发。
3. 策略参数覆盖在前端 `index.vue` 的 `applyStrategyParamMapping()` 中完成：前端调用 `/system/strategy/name/{strategyName}` 取得记录后覆盖 `payload.config`，再将最终配置发送给 Admin。
4. `ClientMessageRouter` 与 `EngineRequestController` 负责请求标识、来源字段和 Engine 转发；后端当前不会再次应用策略。

## 第一部分：节点编辑管理

## 1. 节点编辑管理概述

**节点编辑管理模块**是 Admin 后台中新增的一个菜单入口，用来以“新手友好”的方式展示和调用 Engine 侧基于 Playwright 实现的元器自动化能力。  

从整体视角看，可以把它理解为一个 **“浏览器自动化能力展示与调度中心”**：

```text
┌─────────────────────────┐
│      节点编辑页面       │  ← Admin UI：卡片 + 表单
└─────────────┬───────────┘
              │ YUANQI_* 请求 (WebSocket / HTTP)
              ▼
┌─────────────────────────┐
│   前端：策略参数覆盖    │  ← index.vue /system/strategy/name/{name}
│   Admin：消息路由层     │  ← ClientMessageRouter / EngineRequestController
└─────────────┬───────────┘
              │ EngineMessage
              ▼
┌─────────────────────────┐
│   Engine：YuanQiNode*   │  ← Controller + YuanQiNodeUtil
│   登录 / 导航 / 编辑等  │  ← Playwright 自动化
└─────────────┬───────────┘
              │ 浏览器操作
              ▼
┌─────────────────────────┐
│     元器网页（前台）    │  ← 实际点击"编辑 / 调试 / 发布"
└─────────────────────────┘
```

Engine 当前注册 3 个与元器工作流相关的能力：

- **节点编辑**：通过浏览器自动化打开元器工作流编辑页，定位大模型节点，修改模型参数与提示词。
- **工作流调试**：在元器侧点击"调试 / 去调试"，填写调试输入，等待运行结果，并把截图与结果回传到前端。
- **工作流发布**：在元器侧执行完整发布流程，监控发布状态，最终返回发布结果。

节点编辑管理的目标：

- 把原本散落在 Engine 代码里的 Playwright 自动化流程，用 **结构化卡片** 的方式暴露给业务同学。  
- 为后续扩展更多"浏览器侧自动化能力"（例如批量配置、可视化巡检）提供统一入口。  
- 支持与策略管理联动：页面在发送前把选中策略覆盖到模型参数中。

## 2. 使用场景

- **新手快速了解 Engine 能力**：通过节点编辑管理界面，可以一目了然地看到 Engine 目前支持的元器操作（编辑 / 调试 / 发布）。  
- **本地联调与冒烟测试**：在不改任何业务代码的前提下，通过节点编辑管理执行一次完整的元器工作流调试 / 发布流程，验证：
  - Engine ⟷ Admin WebSocket 通路是否正常；
  - Playwright 能否正常启动浏览器并登录元器；
  - 工作流页面结构是否与预期一致。
- **为后续"策略管理 + 自动化运维"铺路**：节点编辑管理调用的底层，就是 YuanQiNodeUtil 中的编辑 / 调试 / 发布流程，后续策略只需改 Admin 侧参数，即可快速复用。

## 3. 模块结构与关键文件

### 3.1 前端（Admin UI）

| 文件 | 作用 |
|------|------|
| `WxFbsir-ui/src/views/business/content/NodeEditWithStrategy/index.vue` | 节点编辑页面；使用 WebSocket 发送编辑、发布请求，并在发送前应用策略 |
| `WxFbsir-ui/src/views/business/content/NodeEditWithStrategy/strategy.vue` | 策略管理页面 |

`index.vue` 中为每个能力定义了：

- `id`：能力标识（如 `yuanqi-edit-node`）
- `messageType`：发往 Engine 的类型（如 `YUANQI_EDIT_NODE` / `YUANQI_DEBUG_WORKFLOW` / `YUANQI_PUBLISH_WORKFLOW`）
- `timeout`：前端建议超时时间（秒），会透传到 Engine
- `defaultPayload`：示例参数（spaceName、agentName、workflowName、debugInput 等）

### 3.2 Admin WebSocket 层

| 文件 | 作用 |
|------|------|
| `WxFbsir-business/src/main/java/com/wx/fbsir/business/websocket/server/ClientMessageRouter.java` | 前端 → Admin 的 WebSocket 消息路由器，负责把节点编辑管理发来的消息转发到 Engine |
| `WxFbsir-business/src/main/java/com/wx/fbsir/business/websocket/controller/EngineRequestController.java` | HTTP 转发入口，用于在不走 WebSocket 的场景下直连 Engine |

这两个入口负责给消息补充请求标识、来源信息并转发给指定 Engine；策略参数由前端在调用前处理。

### 3.3 Engine 控制层与自动化工具

| 文件 | 作用 |
|------|------|
| `WxFbsir-engine/src/main/java/com/wx/fbsir/engine/controller/yuanqi/YuanQiNodeController.java` | Engine 侧元器节点相关能力控制器，暴露 `YUANQI_EDIT_NODE` / `YUANQI_DEBUG_WORKFLOW` / `YUANQI_PUBLISH_WORKFLOW` 能力 |
| `WxFbsir-engine/src/main/java/com/wx/fbsir/engine/utils/yuanqi/YuanQiNodeUtil.java` | Playwright 自动化核心工具类，实现编辑节点、调试、发布的完整浏览器操作流程 |
| `WxFbsir-engine/src/main/java/com/wx/fbsir/engine/utils/yuanqi/YuanQiLoginUtil.java` | 封装元器登录与首页导航逻辑（只调用，不修改） |
| `WxFbsir-engine/src/main/java/com/wx/fbsir/engine/utils/yuanqi/YuanQiWorkflowUtil.java` | 封装"导航到工作流编辑页"的通用流程（只调用，不修改） |

## 5. 核心调用流程

下面以 Engine 的"工作流调试（YUANQI_DEBUG_WORKFLOW）"能力为例说明链路；当前节点编辑页面直接使用编辑与发布能力，其他调用方可通过 WebSocket 或 HTTP 转发入口调用调试能力。

```text
调用方（节点编辑页面或其他已认证客户端）
    │ 组装 payload（含 spaceName/agentName/workflowName/...）
    │ 当前页面通过 WebSocket 发送；HTTP 入口为 /ws/engine/request
    ▼
Admin：ClientMessageRouter / EngineRequestController
    │ 补充 requestId、userId、sourceType 等链路字段
    │ 通过 WebSocket 将消息转发到指定 Engine
    ▼
Engine：YuanQiNodeController.handleDebugWorkflow
    │ 创建流式任务 → 持续推送 TASK_LOG / 截图 / 结果
    │ 使用 YuanQiLoginUtil 登录并进入工作空间
    │ 使用 YuanQiWorkflowUtil 导航到工作流编辑页
    │ 调用 YuanQiNodeUtil.debugWorkflow(...) 执行真实调试
    ▼
元器网页（浏览器中实际执行调试）
```

### 5.1 前端发起请求

- 构造消息：`type = "YUANQI_DEBUG_WORKFLOW"`，指定 `engineId` 与 `payload`。  
- `payload` 中包含：`spaceName`、`agentName`、`workflowName`、`debugInput`、`timeout` 等信息。  

### 5.2 Admin 转发与来源追踪

- `ClientMessageRouter` / `EngineRequestController`：
  - 校验并补充 `engineId`、`type`、`payload` 所需的链路字段。
  - 生成 `requestId` 并写入 `sourceType`（WebSocket 或 HTTP），使结果可以回到正确来源。
  - 通过 WebSocket 将消息转发到指定 Engine。  

### 5.3 Engine 执行调试 / 发布 / 编辑

- `YuanQiNodeController`：
  - 使用 `startStreamTask` 启动流式任务，给前端持续推送日志与截图。  
  - 通过 `YuanQiLoginUtil` 确保已登录元器，并导航到工作流编辑页。  
  - 根据能力类型调用 `YuanQiNodeUtil` 对应方法：
    - `editLLMNode(...)`：编辑大模型节点参数与提示词。  
    - `debugWorkflow(...)`：执行"调试"流程并等待结果（支持自定义超时时间）。  
    - `publishAgent(...)`：执行发布流程（含多轮状态检测与截图）。

## 6. 操作指引：如何使用节点编辑

1. 登录福帮手 Admin 后台，进入 **"主机管理 → 工作流节点编辑"**。  
2. 在卡片列表中选择：
   - **节点编辑**：适合调整模型与提示词；
   - **工作流调试**：适合验证当前参数能否在元器顺利跑通；
   - **工作流发布**：用于将工作流正式发布。  
3. 填写或确认默认参数：空间名、智能体名、工作流名、节点名、策略名（可选）、超时时间等。  
4. 点击"运行"按钮：
   - 前端会在右侧或弹窗区域展示任务进度、截图与最终结果。  
   - 如果 Engine 侧发生异常，会以错误日志 + 截图的形式回传，便于排查。

## 7. 能力清单与字段说明

### 7.1 节点编辑管理卡片一览

| 能力ID (`id`) | 消息类型 (`messageType`) | 主要功能 | 对应 Engine 能力 | 典型场景 |
|--------------|-------------------------|----------|------------------|----------|
| `yuanqi-edit-node` | `YUANQI_EDIT_NODE` | 打开元器工作流编辑页，自动选中某个大模型节点并按策略填充参数与提示词 | `YuanQiNodeController.handleEditNode` → `YuanQiNodeUtil.editLLMNode` | 批量调整模型/提示词、验证策略配置是否生效 |
| `yuanqi-debug-workflow` | `YUANQI_DEBUG_WORKFLOW` | 在元器中执行一次"调试 / 去调试"，自动填充输入并等待输出 | `YuanQiNodeController.handleDebugWorkflow` → `YuanQiNodeUtil.debugWorkflow` | 回归测试工作流是否能跑通、调参后验证效果 |
| `yuanqi-pyzx-publish` / `yuanqi-publish-workflow` | `YUANQI_PUBLISH_WORKFLOW` | 打开智能体详情页，一键执行发布流程，检查"已发布"状态 | `YuanQiNodeController.handlePublishWorkflow` → `YuanQiNodeUtil.publishAgent / publishWorkflow` | 将测试通过的工作流发布到线上环境 |

> 实际 ID 以 `index.vue` 中配置为准，上表用于帮助快速对号入座。  

### 7.2 请求字段说明（以 YUANQI_EDIT_NODE 为例）

```jsonc
{
  "type": "YUANQI_EDIT_NODE",
  "engineId": "engine-001",
  "payload": {
    "spaceName": "福帮手开源",         // 元器中的空间名称
    "agentName": "日更助手1",          // 智能体名称
    "workflowName": "日更助手-高优先级",
    "nodeName": "混元大模型",          // 需要编辑的节点名称
    "strategy": "成本优先",            // 可选：策略名称（对应策略管理中的 strategyName）
    "timeout": 90,                    // 超时时间（秒），用于 Engine 端总超时控制
    "config": {                       // 将要应用到节点的参数集合（可被策略覆盖）
      "modelName": "混元大模型长文本版",
      "temperature": 0.4,
      "topP": 0.8,
      "maxTokens": 4000,
      "prompt": "这里是提示词模板，支持 {{变量1}} 占位符"
    }
  }
}
```

**字段要点**：

- **spaceName / agentName / workflowName / nodeName**：必须与元器页面展示的文案一致，否则自动化脚本无法定位元素；  
- **strategy**：若不传或为空，则不会触发策略覆盖，直接使用 `config` 中的原始值（详见第二部分策略管理）；  
- **timeout**：前端可按业务时长设置（如 60/90/120 秒），Engine 端会把它转换为毫秒，作为 `debugWorkflow` / `publishWorkflow` / `editLLMNode` 的总超时时间。

## 8. 时序图与运行时行为

### 8.1 YUANQI_DEBUG_WORKFLOW 时序图

```text
已认证调用方请求「工作流调试」
    │
    │ 1. 组装 payload（含 spaceName/agentName/workflowName/debugInput/timeout）
    ▼
前端调试页或其他调用方
    │ send({ type: 'YUANQI_DEBUG_WORKFLOW', payload })
    ▼
ClientMessageRouter（Admin）
    │ 生成 requestId/sourceType 并转发
    │ 通过 WebSocket 转发到指定 Engine (engineId)
    ▼
Engine WebSocketClientManager → YuanQiNodeController.handleDebugWorkflow
    │ startStreamTask()  -> 持续推送 TASK_LOG / 截图 / 最终结果
    │ loginUtil.navigateToHomePage() + checkLoginStatus()
    │ workflowUtil.navigateToWorkflowEdit()
    │ nodeUtil.debugWorkflow(page, debugInput, userId, timeoutSeconds)
    │   ├─ 点击「调试」→「去调试」
    │   ├─ 查找对话输入框并输入 debugInput
    │   ├─ 按 Enter 触发运行
    │   ├─ 循环检测：失败提示 / 输出内容 / 「运行完成」状态
    │   └─ 超时则返回「调试超时（已等待X秒）」
    ▼
前端 WebSocket
    └─ 实时展示日志与截图，最终弹出"调试完成 / 失败 / 超时"结果
```

### 8.2 超时与重试策略

- **前端超时（UI超时）**：`index.vue` 中每个能力卡片有 `timeout` 字段，用于控制前端等待 WebSocket 结果的时间；  
- **Engine 总体超时**：
  - `debugWorkflow(Page page, Map<String,Object> debugInput, String userId, Integer timeoutSeconds)`：
    - 默认 90 秒，可由前端 `payload.timeout` 覆盖；  
    - 通过 `while (now - start < timeoutMs)` 循环检查运行状态，超时即返回失败结果并附带截图。  
  - `publishWorkflow(Page page, Integer timeoutSeconds)`：
    - 按 `timeoutSeconds` 计算检查次数：每 5 秒轮询一次"已发布/发布成功"等状态；  
    - **超时兜底逻辑**：如果超时了还没有检测到发布成功或已发布，返回"待审核"状态，表示发布操作已执行，但需要人工确认最终状态；  
  - `editLLMNode(..., Integer timeoutSeconds)`：
    - 引入 `deadlineMs` 概念，所有 `waitForTimeout` / `waitForLoadState` 都通过 `safeWait` 裁剪，保证整体执行时间不超过 `timeoutSeconds`；  
    - **参数设置优化**：只在第一次打开面板，然后连续设置所有参数，减少面板打开次数和等待时间；  
    - **输入操作优化**：使用 `focus()` 而不是 `click()` 来聚焦输入框，减少意外触发面板关闭的风险。  

> 建议：根据实际网络情况和工作流复杂度，适当放大 `timeout`（例如 90~180 秒），避免长流程误判为超时。

### 8.3 发布功能导航优化

**空间选择后的等待机制**：

在 `navigateToAgentDetail` 方法中，选择空间后会等待 2 秒，确保页面加载完成：

```java
spaceOption.click();
// 等待页面加载完成，防止过早检测导致检测不到智能体
log.debug("[元器导航] 已选择空间，等待页面加载完成（2秒）");
page.waitForTimeout(2000);
```

**优化原因**：
- 空间切换后，页面需要时间加载智能体列表
- 过早检测可能导致无法找到目标智能体
- 2 秒等待确保页面状态稳定后再进行后续操作

**即使未找到空间选项也等待**：
- 如果空间选项未找到（可能已在当前空间），也会等待 2 秒，确保页面状态稳定

## 9. 常见问题与排查示例

### 9.1 无法定位到指定智能体 / 节点

- **症状**：任务日志中出现 `未找到节点: xxx`、`导航失败: 未找到指定空间或智能体`；  
- **排查步骤**：  
  - 确认 `spaceName` / `agentName` / `workflowName` / `nodeName` 与元器页面显示文案完全一致（含空格、大小写）；  
  - 查看 `YuanQiNodeUtil` 日志中 `findNode` / `navigateToAgentDetail` 等日志，确认是否有"找到 N 个候选元素"；  
  - 如页面结构变更，可在浏览器中按 `F12` 查看对应 DOM 结构，并在 `YuanQiNodeUtil` 中调整选择器。  

### 9.2 调试一直等待到超时，未检测到"运行完成"

- **症状**：调试页面实际已经出现绿色"运行完成"，但前端仍显示超时；  
- **实现机制**：`debugWorkflow` 中的成功检测逻辑分三层：
  1. 检查失败状态（`isRunFailed`）；  
  2. 从页面提取输出文本（`extractDebugOutput`）；  
  3. 检查页面中是否存在"已完成 / 运行完成 / 发布成功"等关键文案或样式。  
- **处理建议**：  
  - 打开 Engine 日志，搜索 `[元器工作流调试]` 与 `debug_timeout` 关键词，查看最后一次截图确认页面状态；  
  - 如页面文案变更（例如从"运行完成"改为"执行成功"），在 `YuanQiNodeUtil` 中补充新的关键字匹配逻辑。  

### 9.3 发布成功但前端提示"发布超时"

- **原因**：元器后台执行时间超过了前端 / Engine 的超时时间，导致本次调用返回"发布超时（已等待X秒）"，但实际上稍后工作流已成功发布；  
- **解决建议**：  
  - 适当提高 `timeout`，例如从 60 秒提高到 120 秒；  
  - 或在多次观察后将元器端的发布时长纳入评估，合理设置默认超时时间；  
  - **注意**：当前版本中，如果超时了还没有检测到发布成功或已发布，会返回"待审核"状态，表示发布操作已执行，但需要人工确认最终状态。

### 9.4 参数设置时面板意外关闭

- **症状**：设置 temperature 后，面板被关闭，导致后续 topP 和 maxTokens 无法设置；  
- **原因**：使用 `click()` 操作输入框可能触发某些事件，导致面板关闭；  
- **解决方案**：
  - Engine 侧已优化：使用 `focus()` 而不是 `click()` 来聚焦输入框，减少意外触发面板关闭的风险；
  - 如果面板已关闭，会在设置下一个参数前重新打开面板；
  - 参数设置流程优化：只在第一次打开面板，然后连续设置所有参数，减少面板打开次数。

### 9.5 提示词输入框检测失败

- **症状**：提示词配置逻辑未执行，日志显示"未找到输入框"；  
- **原因**：提示词输入框在页面底部，需要滚动才能看到；  
- **解决方案**：
  - Engine 侧已优化：在处理提示词前，先将整个页面缩小 50%，提高输入框可见性；
  - 增加滚动次数和滚动距离，确保能够滚动到页面底部；
  - 鼠标移动到配置面板中心后再滚动，确保滚轮事件发生在正确的容器内；
  - 多次尝试查找输入框，即使不可见也尝试使用。

## 10. Engine 侧核心优化说明

### 10.1 参数设置流程优化

**优化内容**：

1. **智能面板检测**：
   - 通过检测关键元素（"选择模型"、"重置参数"、"参数"、"温度"、"Top P"、"最大回复Token"）判断面板是否已打开
   - 如果面板已打开，直接连续设置所有参数，无需重复打开

2. **参数设置流程**：
   ```text
   检查是否需要设置参数
       ↓
   检测面板是否已打开
       ↓
   如果未打开 → 打开面板 → 等待200ms
       ↓
   连续设置所有参数（temperature → topP → maxTokens）
       ↓
   每个参数设置后等待80ms
       ↓
   所有参数设置完成后，点击空白处关闭面板
   ```

3. **输入操作优化**：
   - 使用 `focus()` 而不是 `click()` 来聚焦输入框
   - 如果 `focus()` 失败，再回退到 `click()` 操作
   - 减少意外触发面板关闭的风险

### 10.2 发布功能导航优化

**空间选择等待机制**：

在 `navigateToAgentDetail` 方法中，选择空间后会等待 2 秒：

```java
spaceOption.click();
// 等待页面加载完成，防止过早检测导致检测不到智能体
log.debug("[元器导航] 已选择空间，等待页面加载完成（2秒）");
page.waitForTimeout(2000);
```

**优化原因**：
- 空间切换后，页面需要时间加载智能体列表
- 过早检测可能导致无法找到目标智能体
- 2 秒等待确保页面状态稳定后再进行后续操作

### 10.3 提示词处理优化

**页面缩放**：
- 在处理提示词前，先将整个页面缩小 50%（`zoom = 0.5`）
- 等待 1 秒让页面渲染调整完成
- 提高输入框可见性，便于检测和操作

**滚动检测**：
- 增加滚动次数（从 10 次增加到 24 次）
- 增加滚动距离（从 200px 增加到 260px）
- 鼠标移动到配置面板中心后再滚动，确保滚轮事件发生在正确的容器内
- 多次尝试查找输入框，即使不可见也尝试使用

## 第二部分：策略管理

## 11. 策略管理概述

**策略管理模块**用于将"模型名称 + 温度 + TopP + MaxTokens + 提示词模板"等一组参数抽象为一个 **策略（Strategy）**。当前节点编辑页面会在请求 Engine 前取回策略并合并参数，Engine 只接收合并后的 `config`。

从整体链路看，策略查询与参数覆盖位于前端调用层：

```text
┌────────────────────────────┐
│ 节点编辑页面 index.vue       │
│ 输入：strategy + config      │
└──────────────┬─────────────┘
               │ GET /system/strategy/name/{name}
               ▼
┌────────────────────────────┐
│ 前端 applyStrategyParamMapping│
│ 用非空字段覆盖最终 config    │
└──────────────┬─────────────┘
               │ YUANQI_EDIT_NODE（WebSocket）
               ▼
┌────────────────────────────┐
│ Admin 路由 → Engine          │
│ 保留最终 config 并补充链路字段 │
└──────────────┬─────────────┘
               │ Playwright 自动化
               ▼
┌────────────────────────────┐
│ 元器工作流编辑页面            │
└────────────────────────────┘
```

当前版本中，策略管理主要服务于：

- **元器工作流大模型节点编辑**：
  - 前端在调用 `YUANQI_EDIT_NODE` 前，若填写策略名（如"成本优先"、"效果优先"），会查询策略记录并把非空字段覆盖到 `payload.config` 中；
  - Admin 按原样转发最终 `config`，Engine 侧只操作最终生效的配置。

设计目标：

- 把"如何配模型、如何写提示词"从代码中抽离，交给 **可视化的策略管理页面**；  
- 让不同业务线可以共享一套策略配置，避免复制粘贴参数。  

---

## 12. 核心概念

### 12.1 策略（Strategy）

策略是一个 **命名好的参数模板**，包含但不限于：

| 字段 | 说明 |
|------|------|
| `strategyName` | 策略名称，业务唯一，如 `成本优先` / `效果优先` |
| `modelName` | 元器大模型名称，如"混元大模型长文本版" |
| `temperature` | 采样温度 |
| `topP` | TopP 采样参数 |
| `maxTokens` | 最大生成长度 |
| `prompt` | 提示词模板，支持变量占位符（见第 17 章） |

### 12.2 参数覆盖规则

- 只有当 **前端 payload 中显式传入 `strategy` 字段** 时，才会执行策略查找和覆盖；  
- 查到的策略只会对 `config` 中的这几个字段进行覆盖：
  - `modelName` / `temperature` / `topP` / `maxTokens` / `prompt`；  
- 如果某个字段在策略中为 `null`，则不覆盖该字段，保留原始 `config` 值；  
- 查不到策略时，仅记录 WARN 日志，不抛异常，继续使用原始参数。  

---

## 13. 策略管理数据库设计

### 13.1 策略参数表

策略数据存储在 `strategy_param_mapping` 表中（通过 `sql/menu_init.sql` 初始化）：

- 主要字段：
  - `id`：主键；  
  - `strategy_name`：策略名（唯一索引）；  
  - `model_name` / `temperature` / `top_p` / `max_tokens` / `prompt` 等。  

> 该表通过 `IStrategyParamMappingService` 暴露到业务层，其具体实现位于系统模块中，策略管理只依赖接口，不直接操作 Mapper。  

### 13.2 菜单与权限（策略管理）

以下 SQL 负责将"策略管理"菜单挂载到 Admin 后台（已合并到统一 SQL 文件中）：

- `sql/menu_init.sql`：
  - 在 `sys_menu` 中新增"策略管理"菜单及其增 / 删 / 改 / 查按钮；  
  - 在 `sys_role_menu` 中为管理员角色绑定策略管理权限；  
  - 所有 `INSERT` 均带 `ON DUPLICATE KEY UPDATE`，方便多次执行。  

### 13.3 与节点编辑的关系

节点编辑管理（见第一部分）会把用户选择的策略名写入 `payload.strategy`；在真正发送消息前，`index.vue` 会先查询策略并把非空字段合并到 `payload.config`。

## 15. 与节点编辑的关系

### 15.1 调用链路

```text
前端节点编辑管理/业务页面
    ↓  查询策略并合并 config（type = YUANQI_EDIT_NODE）
Admin：ClientMessageRouter / EngineRequestController
    ↓  转发最终 config，并记录 requestId/sourceType
Engine：YuanQiNodeController.handleEditNode()
    ↓
Engine：YuanQiNodeUtil.editLLMNode(...) 读取 config 中的最终参数
    ↓
浏览器中的元器工作流编辑页（Playwright 自动化执行）
```

### 15.2 Engine 的无感知设计

- Engine 不直接依赖策略表，不感知"策略名"；  
- `YuanQiNodeUtil.editLLMNode` 只关心 `config` 中的具体参数（如 `modelName`、`prompt`），因此策略机制不会侵入 Engine 逻辑；  
- 这样可以在不重新部署 Engine 的情况下，通过修改策略表，快速调整模型与提示词。

## 16. 使用指南：如何配置与使用策略

### 16.1 新建策略

1. 登录 Admin，进入 **"主机管理 → 策略管理"** 页面；  
2. 点击"新增策略"，填写：
   - 策略名称（如"成本优先"、"效果优先"）；  
   - 模型名称、temperature、topP、maxTokens；  
   - 提示词模板（支持变量占位符，见第 17 章）；  
3. 保存后，数据会写入策略参数表。  

### 16.2 在节点编辑中使用策略

1. 打开 **"主机管理 → 工作流节点编辑"**；  
2. 在"节点编辑"能力的表单中，选择或输入策略名称（应与策略管理中完全一致）；  
3. 点击运行：
   - 前端会查询策略并覆盖表单参数；
   - Engine 会用覆盖后的配置去编辑元器工作流节点。  

### 16.3 在自定义调用中使用策略

如果你在其他模块手动构造 `YUANQI_EDIT_NODE` 请求，需要：

- 先调用 `GET /system/strategy/name/{strategyName}` 取得策略记录；
- 在调用方将策略的非空字段合并到 `config`；
- 将最终 `config` 连同可选的 `strategy` 名称发送。后端当前不会根据该名称再次覆盖参数。

## 17. 变量占位符与提示词模板规范

为方便 Engine 在元器页面中正确插入变量占位符，我们约定：

- 变量使用 `{{名称2}}` 的形式，其中：
  - `名称`：变量含义（如"名称"、"主题"等）；  
  - 末尾数字：变量序号，例如 `{{名称2}}` 表示"第 2 个变量占位符"；  
- 如果 `{{}}` 内不包含数字，则默认为 **1 号变量**；  
- 特殊工作流的最大序号：
  - `日更助手-高优先级`：最大为 1；  
  - `分析助手-高优先级-多模型`：最大为 3。  

Engine 侧在执行节点编辑时，会：

1. 扫描 `prompt` 中所有 `{{...}}`；  
2. 提取每个占位符中的数字，按顺序放入队列；  
3. 在浏览器中真正输入提示词时：
   - 遇到占位符位置 → 输入 `/` 触发元器变量列表；  
   - 按 `ArrowDown` `(ID-1)` 次选择对应变量；  
   - 按 `Enter` 确认插入；  
4. 普通文本按原样逐段输入，**不改变原始提示词字符串**。  

这样既保证了策略提示词的可读性，又保证 Engine 能在元器界面中准确选择对应变量。

## 18. 策略管理常见问题与排查建议

### 18.1 "策略没有生效，参数未被覆盖"

检查步骤：

1. 确认前端在 payload 顶层是否传了 `strategy` 字段；  
2. 确认策略名称与数据库中的 `strategy_name` 完全一致（含大小写与空格）；  
3. 查看浏览器控制台或页面提示中是否有策略查询失败信息；
4. 若发现字段为 `null`，注意：为 `null` 的字段不会覆盖原值。  

### 18.2 "提示词变量没有正确插入到元器页面中"

1. 确认提示词模板是否使用 `{{名称2}}` 这样的规范格式；  
2. 对于 `日更助手-高优先级` 工作流，避免设置大于 1 的序号；  
3. 查看 Engine 日志中 `[元器提示词填充]` 开头的输出，确认是否有占位符解析与键盘模拟过程。
