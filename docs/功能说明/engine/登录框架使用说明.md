## 1. 框架概述

### 1.1 什么是登录框架？

登录框架是一个**通用的、平台无关的登录状态持久化解决方案**，用于解决AI平台登录状态不持久的问题。

**问题背景**：
- ❌ 每次重启服务或关闭浏览器后，用户需要重新扫码登录
- ❌ 不同平台（Gitee、DeepSeek、元器）的登录逻辑重复编写
- ❌ 登录状态管理分散，难以维护

**解决方案**：
- ✅ 登录一次后，自动保存完整的登录状态（Cookies、LocalStorage等）
- ✅ 下次使用时自动恢复，无需重复登录
- ✅ 统一的API接口，支持所有AI平台
- ✅ 企业级的可靠性和性能

### 1.2 核心概念

```
用户扫码登录 → 提取登录状态 → 保存到本地文件 → 下次自动恢复 → 无需重新登录
```

| 概念 | 说明 | 示例 |
|------|------|------|
| **Platform** | 平台标识 | `gitee`, `deepseek`, `yuanqi` |
| **UserId** | 用户ID | `1`, `2`, `103` |
| **LoginState** | 登录状态对象 | 包含Cookies、LocalStorage等 |
| **StorageState** | Playwright存储状态 | 浏览器的完整状态快照 |

## 2. 核心特性

### 2.1 功能特性

| 特性 | 说明 |
|------|------|
| 🌐 **平台无关** | 统一的API，支持Gitee、DeepSeek、元器等所有平台 |
| 📦 **完整性** | 保存Cookies、LocalStorage、SessionStorage等所有登录信息 |
| 💾 **持久化** | 登录状态保存到本地文件，永久有效（由平台自身管理） |
| 🔄 **自动恢复** | 下次使用时自动恢复登录状态，失效时自动重新登录 |
| 🚀 **易扩展** | 新增平台只需调用统一API，无需重复编写持久化逻辑 |
| ⚙️ **配置化** | 直接使用`application.yml`的`data-dir`配置 |
| 🔒 **并发安全** | 不使用锁文件，支持多进程并发访问 |

### 2.2 有效期策略

**框架不检查过期时间**，由各平台自身的登录状态管理机制决定：

```
登录状态文件存在 → 下次使用时自动恢复 → 平台检测登录状态
                                    ↓
                            如果平台判定已失效
                                    ↓
                        登录检测返回未登录 → 用户重新登录
```

**优势**：
- 避免框架与平台的有效期冲突
- 由平台决定有效期，更加灵活
- 用户体验更好（自动失效自动重新登录）

## 3. 快速开始

### 3.1 保存登录状态

在登录成功后调用：

```java
// 在Controller的登录成功处理中
BrowserSession session = browserPool.acquirePersistent(userId, "gitee", false);

// ... 登录逻辑 ...

// 登录成功后，保存登录状态
boolean saved = LoginStateManager.saveLoginState(
    session,           // 浏览器会话
    "gitee",           // 平台标识
    userId,            // 用户ID
    "Gitee用户"        // 用户名（用于日志）
);

if (saved) {
    log.info("✅ 登录状态已保存 - 平台: gitee, 用户: {}", userId);
} else {
    log.warn("⚠️ 登录状态保存失败 - 平台: gitee, 用户: {}", userId);
}
```

### 3.2 恢复登录状态

在创建新会话时调用：

```java
// 在Controller的登录检测或AI咨询中
BrowserSession session = browserPool.acquirePersistent(userId, "gitee", false);

// 检查是否存在登录状态
if (LoginStateManager.hasLoginState("gitee", userId)) {
    // 恢复登录状态
    boolean restored = LoginStateManager.restoreLoginState(
        session,    // 浏览器会话
        "gitee",    // 平台标识
        userId      // 用户ID
    );
    
    if (restored) {
        log.info("✅ 登录状态已恢复 - 平台: gitee, 用户: {}", userId);
    } else {
        log.warn("⚠️ 登录状态恢复失败 - 平台: gitee, 用户: {}", userId);
    }
}

// 继续业务逻辑（导航、检测登录状态等）
```

### 3.3 保存Authorization Header（Bearer Token等）

某些平台使用Bearer Token或API Key进行认证，需要额外保存：

```java
// 登录成功后，保存Authorization Header
LoginStateManager.saveAuthorizationHeader("deepseek", userId, "Bearer xxx");

// 下次使用时获取
String authHeader = LoginStateManager.getAuthorizationHeader("deepseek", userId);
if (authHeader != null) {
    // 在HTTP请求中添加Authorization头
    request.header("Authorization", authHeader);
}
```

### 3.4 清除登录状态

当用户主动登出时调用：

```java
// 清除登录状态
LoginStateManager.clearLoginState("gitee", userId);
log.info("✅ 登录状态已清除 - 平台: gitee, 用户: {}", userId);
```

## 4. 工作原理

### 4.1 保存流程

```
1. 获取BrowserContext的storageState()
   ↓
2. 解析JSON，提取Cookies、LocalStorage、SessionStorage
   ↓
3. 构建LoginState对象，添加元数据（保存时间、用户名等）
   ↓
4. 序列化为JSON，写入本地文件
   ↓
5. 返回保存结果
```

### 4.2 恢复流程

```
1. 从本地文件加载LoginState对象
   ↓
2. 验证文件有效性（存在且valid=true）
   ↓
3. 将Cookies注入到BrowserContext
   ↓
4. 将LocalStorage/SessionStorage通过JavaScript注入
   ↓
5. 返回恢复结果
```

### 4.3 关键类说明

| 类名 | 位置 | 职责 |
|------|------|------|
| **LoginState** | `model/` | 登录状态数据模型 |
| **LoginStatePersistence** | `persistence/` | 文件读写操作 |
| **LoginStateRestorer** | `restorer/` | 状态恢复到浏览器 |
| **LoginStateManager** | `manager/` | 统一管理门面（推荐使用） |

## 6. 常见问题

### Q1: 登录状态什么时候过期？

**A**: 框架不检查过期时间。由各平台自身决定：
- 如果平台的登录状态失效，下次登录检测会返回未登录
- 用户检测到未登录时，会自动调用登录逻辑重新登录
- 框架只负责保存和恢复，不判断是否过期

### Q2: 如何添加新的AI平台？

**A**: 只需3步：

```java
// 1. 登录成功后保存
LoginStateManager.saveLoginState(session, "新平台名", userId, userName);

// 2. 创建会话时恢复
if (LoginStateManager.hasLoginState("新平台名", userId)) {
    LoginStateManager.restoreLoginState(session, "新平台名", userId);
}

// 3. 用户登出时清除
LoginStateManager.clearLoginState("新平台名", userId);
```

无需修改框架代码，完全兼容！

### Q3: 登录状态文件被删除了怎么办？

**A**: 框架会自动处理：
- 检测到文件不存在时，`hasLoginState()`返回`false`
- 下次使用时会提示用户重新登录
- 用户重新登录后，框架会重新保存登录状态

### Q4: 多个用户同时登录会冲突吗？

**A**: 不会。框架按`{data-dir}/{platform}/user-{userId}/`分离存储：
- 每个用户的登录状态独立保存
- 支持多用户并发访问
- 不使用锁文件，避免死锁

### Q5: 如何验证登录状态是否有效？

**A**: 只有一种方式——**通过页面打开后的登录检测**：

```java
// ✅ 唯一有效的判断方式：
// 1. 尝试恢复登录状态
boolean restored = LoginStateManager.restoreLoginState(session, "gitee", userId);

// 2. 打开页面进行登录检测
Page page = session.getOrCreatePage();
page.navigate("https://chat.gitee.com/");

// 3. 检查页面上的登录标志（如头像、用户名等）
// 如果检测到登录标志 → 登录状态有效
// 如果未检测到登录标志 → 登录状态已失效，需要重新登录
```

**为什么不能只检查文件？**
- ❌ 文件存在 ≠ 平台服务器上的登录状态有效
- ❌ 登录状态可能在服务器端已过期
- ✅ 只有实际打开页面后，才能确认登录状态是否真正有效

## 已知限制与故障排查

### 已支持的浏览器存储方式

✅ **完全支持**：
- **Cookies** - 所有属性（domain、path、expires、httpOnly、secure、sameSite）
- **LocalStorage** - 按Origin分组，支持页面加载前后恢复
- **SessionStorage** - 按Origin分组，支持页面加载前后恢复
- **Authorization Header** - Bearer Token、API Key等认证信息（P0完善）

### 部分不常用的存储方式（未支持）

❌ **暂不支持**（后续遇到需求时考虑完善）：

| 存储方式 | 说明 | 影响范围 | 解决方案 |
|---------|------|---------|---------|
| **IndexedDB** | 某些现代Web应用使用的大容量数据库 | 少数AI平台 | 需要导出/导入数据库数据 |
| **WebSQL** | 已废弃，某些旧应用仍在使用 | 极少数平台 | 不建议支持 |
| **Service Worker** | PWA应用的离线能力 | 少数平台 | 需要重新注册Service Worker |
| **跨域iframe存储** | iframe内的Cookies和Storage | 少数平台 | 需要特殊处理跨域问题 |

### 故障排查指南

#### 情况1：登录状态保存失败

**可能原因**：
- ❌ 文件系统权限不足
- ❌ 磁盘空间不足
- ❌ 路径配置错误

**排查步骤**：
```
1. 查看日志中的错误信息
   [登录状态持久化] ❌ 保存失败 - 错误: xxx

2. 检查文件路径配置
   application.yml: playwright.data-dir: ./data/playwright

3. 检查目录权限
   ls -la ./data/playwright/

4. 确保有足够的磁盘空间
   df -h
```

#### 情况2：登录状态恢复失败

**可能原因**：
- ❌ 登录状态文件已损坏
- ❌ 登录状态已过期（平台服务器判定）
- ❌ LocalStorage/SessionStorage恢复时序问题

**排查步骤**：
```
1. 检查文件是否存在
   ls -la ./data/playwright/gitee/user-1/login-state.json

2. 检查文件内容是否有效
   cat ./data/playwright/gitee/user-1/login-state.json | jq .

3. 检查页面加载时序
   - 如果平台在页面加载前就需要LocalStorage，使用：
     LoginStateRestorer.restoreStorageBeforeNavigation(context, loginState);
   - 如果平台在页面加载后才需要，使用：
     LoginStateRestorer.restoreStorageToPage(page, loginState);

4. 打开页面检测登录状态
   - 页面上有登录标志（头像、用户名等）→ 登录状态有效
   - 页面上无登录标志 → 登录状态已失效，需要重新登录
```

#### 情况3：某些平台登录状态保存不完整

**可能原因**：
- ❌ 平台使用IndexedDB存储数据
- ❌ 平台使用Authorization Header认证
- ❌ 平台使用自定义HTTP请求头

**解决方案**：

**方案A：保存Authorization Header**
```java
// 登录成功后获取Token
String token = extractTokenFromPage(page);

// 保存Authorization Header
LoginStateManager.saveAuthorizationHeader("platform", userId, "Bearer " + token);

// 下次使用时恢复
String authHeader = LoginStateManager.getAuthorizationHeader("platform", userId);
```

**方案B：保存自定义HTTP请求头**
```java
// 保存任何自定义请求头
LoginStateManager.saveCustomHeader("platform", userId, "X-CSRF-Token", csrfToken);
LoginStateManager.saveCustomHeader("platform", userId, "X-API-Key", apiKey);

// 下次使用时恢复
String csrfToken = LoginStateManager.getCustomHeader("platform", userId, "X-CSRF-Token");
String apiKey = LoginStateManager.getCustomHeader("platform", userId, "X-API-Key");
```

**方案C：如果需要IndexedDB支持**
```
1. 检查平台是否真的需要IndexedDB
   - 在浏览器DevTools中查看Application → IndexedDB

2. 如果确实需要，请提出需求
   - 框架会在后续版本中支持IndexedDB导出/导入
```

#### 情况4：页面加载时LocalStorage/SessionStorage为空

**可能原因**：
- ❌ 使用了错误的恢复时机
- ❌ 页面加载前没有恢复Storage

**解决方案**：

```java
// ✅ 正确的做法：在页面导航前恢复Storage
BrowserContext context = session.getContext();

// 1. 恢复Cookies
LoginStateRestorer.restore(session, loginState);

// 2. 在页面导航前恢复LocalStorage/SessionStorage
LoginStateRestorer.restoreStorageBeforeNavigation(context, loginState);

// 3. 现在导航页面，页面加载时就能获取到Storage数据
Page page = session.getOrCreatePage();
page.navigate("https://platform.com/");

// 4. 如果还需要额外的Storage恢复（某些平台），在页面加载后调用
LoginStateRestorer.restoreStorageToPage(page, loginState);
```

遇到登录状态保存失败时，按以下顺序检查：

1. **查看日志** → 找到具体错误信息
