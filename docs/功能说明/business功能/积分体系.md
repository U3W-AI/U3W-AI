# 积分体系

本文档说明 FBS 积分模型、数据流、幂等机制、HMAC-SHA256 安全签名、以及积分相关 API。

---

## 一、积分模型架构

### 1.1 数据存储

积分在两个表中管理：

| 表 | 角色 | 关键字段 |
|----|------|----------|
| `sys_user` | 积分余额 | `points`（当前余额） |
| `wx_points_record` | 积分流水（幂等） | `event_id`（幂等键，唯一索引） |

**积分变动流程（幂等）**：
```
业务层调用 changePoints(eventId)
        ↓
检查 event_id 是否已存在（wx_points_record.uk_event_id）
        ↓
若存在：返回既有余额（幂等）
若不存在：正常执行积分变动
        ↓
插入 wx_points_record（含 event_id）
        ↓
更新 sys_user.points
```

### 1.2 event_id 生成规则

| event_type | event_id 格式 | 示例 |
|------------|---------------|------|
| FIRST_INSTALL | `first_install_{userId}` | `first_install_1` |
| DAILY_LOGIN | `daily_login_{userId}_{date}` | `daily_login_1_2026-04-16` |
| SKILL_CONSUME | `skill_consume_{usageId}` | `skill_consume_12345` |
| ADMIN_GRANT | `admin_grant_{adminId}_{timestamp}` | `admin_grant_1_1713254400` |

**注意**：`/fbs/skill-api/points/earn` 中 `eventId = usageRecordId`（复用幂等模型）。

## 二、积分服务层

### 2.1 IPointsService.changePoints 签名

```java
public interface IPointsService {
    // 原有方法（保持不变）
    public AjaxResult changePoints(Long userId, String ruleCode, Integer changeAmount);
    
    // Skill 消费场景（保持不变）
    public AjaxResult changePoints(Long userId, String ruleCode, Integer changeAmount,
                                   Long scenePackId, String usageRecordId);
    
    // 新增：支持幂等的重载
    public AjaxResult changePoints(Long userId, String ruleCode, Integer changeAmount,
                                   Long scenePackId, String usageRecordId, String eventId);
}
```

### 2.2 changePoints 完整流程

```
1. 免费包：ruleCode 为空 → 直接返回成功（不扣积分）
2. 参数校验：userId 非空
3. 幂等检查：eventId 非空 → 查 wx_points_record.uk_event_id → 已存在则返回既有余额
4. 获取积分规则：ruleCode → wx_points_rule（status="0" 为启用，与惯例相反）
5. 计算实际变动值：changeAmount ?? rule.points_value
6. 查询当前余额：sys_user.points
7. 限频校验：checkLimit() → 失败则返回 "已达到限频上限"
8. 累计上限校验：checkMaxAmount() → 失败则返回 "已达到累计上限"
9. 余额校验（扣减场景）：currentPoints + changeAmount < 0 → 返回 "积分余额不足"
10. 更新余额：sys_user.points = newPoints
11. 插入流水：wx_points_record（含 event_id）
12. 记录限频：markLimit()
13. 返回新余额
```

## 三、HMAC-SHA256 签名机制

### 3.1 认证链路（Filter 顺序）

```
HTTP Request
  │
  ├─ URL 不匹配 /fbs/skill-api/** → filterChain.doFilter()（跳过，走 JWT 链路）
  │
  └─ URL 匹配 /fbs/skill-api/**
       │
       ├─ Step 1：API Key 校验
       │    ├─ X-FBS-API-Key 缺失 → 401 SKILL_API_KEY_INVALID
       │    ├─ Key 不存在 → 401 SKILL_API_KEY_INVALID
       │    └─ Key 已禁用 (status!=1) → 403 SKILL_API_KEY_DISABLED
       │
       ├─ Step 2：时间戳校验
       │    ├─ X-FBS-Timestamp 缺失 → 401 SKILL_API_TIMESTAMP_MISSING
       │    ├─ |serverTime - timestamp| > 5min → 401 SKILL_API_TIMESTAMP_EXPIRED
       │    └─ 时间戳有效 → 继续
       │
       ├─ Step 3：签名校验
       │    ├─ X-FBS-Signature 缺失 → 401 SKILL_API_SIGNATURE_INVALID
       │    ├─ HMAC 重新计算不匹配 → 401 SKILL_API_SIGNATURE_INVALID
       │    └─ 签名匹配 → 继续
       │
       ├─ Step 4：速率限制（现有逻辑不变）
       │    └─ 超限 → 429 SKILL_API_RATE_LIMITED
       │
       └─ Step 5：设置 SecurityContext + chain.doFilter()
```

**校验顺序原则**：先快后慢。API Key 查表（有索引）→ 时间戳解析（纯数学）→ 签名 HMAC 计算（CPU 密集）。

### 3.2 签名格式

**签名消息**：`${timestamp}\n${JSON.stringify(body)}`

- `timestamp`：Unix 毫秒时间戳（`Date.now()`），字符串形式
- `\n`：换行符（LF，不是 CRLF）
- `body`：`JSON.stringify(body)`，与发送的 request body 完全一致

**示例**：

```
timestamp = "1745143200000"
body      = {"userId":1001,"source":"FIRST_INSTALL","amount":10,"usageRecordId":"task-abc123"}

message   = "1745143200000\n{\"userId\":1001,\"source\":\"FIRST_INSTALL\",\"amount\":10,\"usageRecordId\":\"task-abc123\"}"
signature = HMAC-SHA256(apiKey, message) → hex string (64 chars)
```

### 3.3 后端签名校验

```java
public boolean verifySignature(String apiKey, String timestamp, String body, String signature) {
    String message = timestamp + "\n" + body;
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(apiKey.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
    byte[] computed = mac.doFinal(message.getBytes(StandardCharsets.UTF_8));
    String computedHex = Hex.encodeHexString(computed);
    return MessageDigest.isEqual(computedHex.getBytes(), signature.getBytes());
}
```

**关键**：使用 `MessageDigest.isEqual()` 而非 `String.equals()`，防止时序攻击。

### 3.4 时间戳窗口

- **窗口大小**：5 分钟（±5 分钟，共 10 分钟有效窗口）
- **时钟偏差容忍**：客户端与服务器时间差在 5 分钟内均可接受
- **时间戳来源**：`X-FBS-Timestamp` Header，Unix 毫秒时间戳
- **校验逻辑**：`Math.abs(System.currentTimeMillis() - timestamp) > 300_000`

### 3.5 API Key 格式

```
fbs_ + Hex.encodeHexString(SecureRandom(32B))
= fbs_ + 64字符 [0-9a-f]
= 68 字符
```

- 前缀 `fbs_`（4 字符）+ 64 位 hex 字符串（`[0-9a-f]`），总长 68 字符，熵 256 bit
- Skill 端校验正则：`/^fbs_[0-9a-f]{64}$/`
- 数据库字段：`fbs_api_key.api_key VARCHAR(128)`
- API Key 明文存储，不迁移到 SHA-256 hash（HMAC 签名依赖明文）

## 四、积分文件完整性校验

### 4.1 积分文件（credits-ledger.json）

`credits-ledger.json` 是 Skill 侧本地的积分缓存文件：

```json
{
  "user_id": 1,
  "balance": 1000,
  "last_updated": "2026-04-16T12:00:00Z",
  "sync_version": "v1.0.0"
}
```

### 4.2 HMAC 完整性校验

**写入时**：

```javascript
function _computeLedgerHmac(balance, totalEarned, totalSpent, apiKey) {
  const message = JSON.stringify({ balance, total_earned: totalEarned, total_spent: totalSpent });
  return createHmac('sha256', apiKey).update(message).digest('hex');
}

const hmac = apiKey ? _computeLedgerHmac(balance, totalEarned, totalSpent, apiKey) : undefined;
const data = { balance, total_earned: totalEarned, total_spent: totalSpent };
if (hmac) data._hmac = hmac;
fs.writeFileSync(path, JSON.stringify(data, null, 2));
```

**读取时校验**：

```javascript
if (data._hmac && apiKey) {
  const expected = _computeLedgerHmac(data.balance, data.total_earned, data.total_spent, apiKey);
  if (expected !== data._hmac) {
    // HMAC 不匹配 → 文件被篡改
    process.stderr.write('[credits-ledger] HMAC mismatch, local balance reset\n');
    data.balance = 0;
    data._hmacInvalid = true;  // 标记，供 getBalance() 判断需从后端拉取
  }
}
```

**无 API Key 时**：不计算/校验 HMAC（纯本地模式）。

## 五、API 说明

### 5.1 POST /fbs/skill-api/points/earn — 行为积分上报

**功能**：Skill 端在检测到行为积分事件（首次安装、每日登录、完章等）后调用。

**幂等**：`eventId = usageRecordId`，复用 `wx_points_record.uk_event_id`（#10 模型）。

**请求参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userId | Long | 否 | 用户ID（可空，从API Key反查） |
| source | String | 是 | 积分来源编码（如 FIRST_INSTALL, DAILY_LOGIN） |
| amount | Integer | 是 | 积分变动值（正整数） |
| usageRecordId | String | 是 | 使用记录ID（也作为 eventId 幂等键） |

**成功响应**：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "success": true,
    "pointsAmount": 10,
    "remainPoints": 1010,
    "usageRecordId": "task-abc123"
  }
}
```

**失败响应**：

| body.code | 场景 |
|-----------|------|
| 403 | 无法识别用户（API Key 未绑定且未传 userId） |
| 500 | source 为空 |
| 500 | amount 非正整数 |
| 500 | usageRecordId 为空 |
| 500 | 积分规则未配置或已停用 |
| 500 | 已达到限频上限，请稍后再试 |
| 500 | 已达到累计上限，无法继续发放 |

## 八、错误码汇总

| HTTP Status | 错误码 | 说明 | 来源 |
|-------------|--------|------|------|
| 401 | `SKILL_API_KEY_INVALID` | API Key 缺失/不存在 | #5 |
| 401 | `SKILL_API_SIGNATURE_INVALID` | 签名缺失/不匹配 | #15 |
| 401 | `SKILL_API_TIMESTAMP_MISSING` | 时间戳缺失 | #15 |
| 401 | `SKILL_API_TIMESTAMP_EXPIRED` | 时间戳过期 | #15 |
| 403 | `SKILL_API_KEY_DISABLED` | API Key 已禁用 | #5 |
| 429 | `SKILL_API_RATE_LIMITED` | 速率超限 | #5 |
| 500 | - | 积分规则未配置/已停用/限频/累计上限/余额不足 | #10 |

**规则**：所有认证/签名/时间戳失败归 401；Key 状态问题归 403；限流归 429；积分业务失败归 500。
