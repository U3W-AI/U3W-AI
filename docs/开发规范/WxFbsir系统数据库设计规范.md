## 1. 项目概述

### 1.1 项目背景
WxFbsir系统是一个综合性的企业级管理平台，涵盖系统管理、内容管理、积分管理、主机管理、认证申请等多个业务领域。系统采用MySQL数据库作为数据存储层，支持多租户架构和高并发访问。

### 1.2 设计目标
- **一致性**: 确保数据结构的一致性和完整性
- **可扩展性**: 支持未来业务发展的需求
- **性能优化**: 通过合理的索引和表结构设计提高查询效率
- **安全性**: 保障数据安全和权限控制
- **易维护性**: 提供清晰的数据结构和文档说明

## 2. 数据库设计规范

## 1. 总体设计原则

### 1.1 设计目标
- **一致性**: 确保数据结构的一致性和完整性
- **可扩展性**: 支持未来业务发展的需求
- **性能优化**: 通过合理的索引和表结构设计提高查询效率
- **安全性**: 保障数据安全和权限控制
- **易维护性**: 提供清晰的数据结构和文档说明

### 1.2 设计哲学
- 遵循单一职责原则，每个表只负责一个业务领域的数据
- 采用规范化设计，减少数据冗余
- 考虑性能和可读性的平衡
- 保证数据完整性和一致性

## 2. 命名规范

### 2.1 表命名规范
根据项目规范，数据库表命名应遵循模块前缀规则：
- **系统表**: 以 `sys_` 为前缀，如 `sys_user`（用户表）、`sys_menu`（菜单表）
- **业务表**: 以具体业务模块名为前缀，如 `daily_article`（日更助手文章表）、`certificate_template`（证书模板表）
- **中间关联表**: 由两个关联表名组合而成，如 `sys_user_role`（用户角色关联表）
- **日志表**: 以 `_log` 结尾，如 `sys_job_log`（定时任务日志表）

### 2.2 字段命名规范
根据项目规范，字段命名遵循以下规则：
- **主键**: 统一使用 `{表名}_id` 或 id，如 `user_id`、`menu_id`
- **外键**: 使用关联表的主键名，如 `user_id`、`role_id`
- **时间字段**: 
  - 创建时间: `create_time`
  - 更新时间: `update_time`
- **状态字段**: status (根据业务含义，如0正常, 1停用/失败)
- **删除标志**: `del_flag` (0正常, 1删除, 2删除)

### 2.3 索引命名规范
根据项目规范，索引命名遵循以下规则：
- **唯一索引**: 以 `uk_` 为前缀，如 `uk_user_id`、`uk_strategy_name`
- **普通索引**: 以 `idx_` 为前缀，如 `idx_user_id`、`idx_create_time`
- **复合索引**: 包含多个字段的含义，如 `idx_user_create_time`

### 2.4 命名最佳实践
- 使用有意义的英文单词，避免缩写（除非是广泛认可的缩写）
- 保持命名风格一致
- 避免使用数据库保留字
- 字段名应反映其业务含义

## 3. 数据类型规范

### 3.1 数值类型规范
- **主键ID**: `bigint(20)` - 支持大数据量
- **状态字段**: `char(1)` 或 `tinyint(1)` - 存储少量枚举值
- **排序字段**: `int(4)` - 支持较大排序值
- **计数字段**: `int(11)` - 支持较大数值
- **金额字段**: `decimal(p,s)` - 精确计算

### 3.2 字符串类型规范
- **短文本**: `varchar(n)` - 一般不超过255字符
- **中等文本**: `varchar(500)` - 适用于描述、备注等
- **长文本**: `longtext` - 适用于内容、JSON等大数据
- **固定长度**: `char(n)` - 适用于状态码等固定长度数据

### 3.3 时间类型规范
- **精确到秒**: `datetime` - 适用于业务时间记录
- **带时区**: timestamp - 适用于需要时区转换的时间

### 3.4 二进制类型规范
- **小文件**: `varbinary` - 适用于较小的二进制数据
- **大文件**: `longblob` - 适用于较大的二进制对象

## 4. 表结构设计规范

### 4.1 通用字段规范
每个业务表应包含以下通用字段：
```
-- 基础审计字段
create_by     varchar(64)  DEFAULT '' COMMENT '创建者'
create_time   datetime     COMMENT '创建时间'
update_by     varchar(64)  DEFAULT '' COMMENT '更新者'
update_time   datetime     COMMENT '更新时间'

-- 可选字段
remark        varchar(500) DEFAULT NULL COMMENT '备注'
```

### 4.2 状态字段规范
- **启用/禁用**: `status char(1) DEFAULT '0' COMMENT '状态（0正常 1停用）'`
- **删除标志**: `del_flag char(1) DEFAULT '0' COMMENT '删除标志（0代表存在 2代表删除）'`
- **业务状态**: 使用具体含义的状态码

### 4.3 字段长度规范
- **用户相关**: 
  - 用户名: `varchar(30)`
  - 邮箱: `varchar(50)`
  - 手机号: `varchar(11)`
- **系统相关**:
  - IP地址: `varchar(128)`
  - URL路径: `varchar(255)`
  - 权限标识: `varchar(100)`

### 4.4 注释规范
- 所有字段必须有中文注释
- 表必须有中文注释
- 注释要准确描述字段/表的业务含义
- 状态字段需在注释中说明各种取值的含义

## 5. 约束和关系规范

### 5.1 主键约束规范
- 每个表必须有主键
- 主键使用自增机制（AUTO_INCREMENT）
- 主键字段不可为空（NOT NULL）
- 主键应为单一字段，避免复合主键

### 5.2 外键约束规范
- 外键字段类型应与关联表主键类型一致
- 外键应建立索引
- 根据业务需求决定是否设置级联操作
- 外键命名应体现关联关系

### 5.3 唯一约束规范
- 业务上要求唯一的字段应添加唯一约束
- 复合唯一约束需谨慎使用
- 唯一约束有助于数据完整性

### 5.4 检查约束规范
- 根据业务规则设置适当的检查约束
- 状态字段可设置值域检查
- 数值字段可设置范围检查

## 6. 索引设计规范

### 6.1 索引设计原则
- 避免过多索引影响写性能
- 优先为经常查询的字段建立索引
- 考虑查询频率和数据更新频率的平衡
- 定期审查和优化索引

### 6.2 索引类型选择
- **单列索引**: 适用于单一字段查询
- **复合索引**: 适用于多字段联合查询
- **唯一索引**: 适用于唯一性约束
- **全文索引**: 适用于文本搜索

### 6.3 复合索引设计
- 遵循最左前缀原则
- 将选择性高的字段放在前面
- 考虑查询模式确定字段顺序
- 避免过长的复合索引

### 6.4 索引性能优化
根据经验教训，避免使用SELECT *，合理建立索引：
- **外键字段**: 建立索引以优化JOIN操作
- **查询条件字段**: 为WHERE子句中的字段建立索引
- **排序字段**: 为ORDER BY子句中的字段建立索引
- **复合索引**: 遵循最左前缀原则，将选择性高的字段放在前面

## 7. 分区设计规范

### 7.1 分区适用场景
- 大数据量表（建议超过百万行）
- 按时间维度查询频繁的表
- 需要定期清理历史数据的表

### 7.2 分区策略
- **按时间分区**: 适用于日志表、历史数据表
- **按范围分区**: 适用于按数值范围查询的场景
- **按哈希分区**: 适用于均匀分布数据的场景

### 7.3 分区实施规范
对大数据量表考虑按时间进行分区，如日志表：
```
-- 示例：按月分区
PARTITION BY RANGE (YEAR(create_time)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026)
);
```

## 8. 安全设计规范

### 8.1 敏感数据保护
- **密码加密**: 使用BCrypt等安全算法加密存储
- **API密钥**: 采用加密存储方式
- **个人信息**: 对敏感信息进行脱敏处理
- **日志记录**: 避免在日志中记录敏感信息

### 8.2 权限控制
- **数据权限**: 通过用户-角色-权限模型控制数据访问
- **操作权限**: 记录操作日志便于审计追踪
- **字段级别权限**: 根据需要控制字段访问权限

### 8.3 SQL注入防护
- 使用参数化查询
- 验证和过滤输入数据
- 避免动态拼接SQL语句

## 9. 性能优化规范

### 9.1 查询优化
- 避免使用SELECT *，明确指定所需字段
- 合理使用索引，避免全表扫描
- 使用LIMIT控制返回数据量
```
SELECT * FROM daily_article ORDER BY create_time DESC LIMIT 20 OFFSET 0;
```

### 9.2 表设计优化
- 适当反范式化以提高查询性能
- 分离热数据和冷数据
- 使用合适的数据类型

### 9.3 批量操作优化
- 批量插入时使用事务
- 避免在循环中执行单条SQL
- 合理设置批量操作大小

## 10. 维护规范

### 10.1 数据归档
- **历史数据**: 定期归档不常用的旧数据
- **日志清理**: 设置自动清理策略，保留必要时长的日志
- **归档策略**: 制定数据生命周期管理策略

### 10.2 监控指标
- **表大小**: 监控各表数据增长趋势
- **索引效率**: 定期分析索引使用情况
- **慢查询**: 监控并优化执行时间过长的SQL语句

### 10.3 备份策略
- 定期备份重要数据
- 验证备份数据的完整性
- 制定灾难恢复计划

## 11. 文档维护规范

### 11.1 变更管理
- **版本控制**: 数据库结构变更纳入Git版本管理
- **变更记录**: 详细记录每次结构变更的原因和影响
- **影响评估**: 评估变更对现有系统功能的影响
- **回滚计划**: 为重要变更制定回滚方案

### 11.2 文档更新
- **及时更新**: 结构变更后及时更新相关文档
- **版本对应**: 确保文档与实际数据库结构保持一致
- **团队共享**: 确保团队成员都能访问最新的设计文档

### 11.3 代码注释
- 在SQL脚本中添加详细的注释
- 说明复杂查询的业务逻辑
- 记录重要的设计决策
