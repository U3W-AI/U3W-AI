### 2. 注释规范

**重要**：所有业务代码必须包含必要的注释，说明业务逻辑和关键处理流程。

#### 2.1 注释原则

**什么时候需要注释**：
- 复杂的业务逻辑
- 重要的设计思路
- 容易出错的地方
- 性能优化的说明

**什么时候不需要注释**：
- 代码本身已经很清楚
- 简单的getter/setter
- 显而易见的逻辑

**核心原则**：
- 注释要说明"为什么"，而不是"做什么"
- 注释要简洁明了
- 注释要与代码保持同步

##### 复杂查询
```sql
-- 查询用户的AI对话统计（最近30天）
SELECT 
  u.user_id,
  u.nick_name,
  COUNT(h.id) AS chat_count,                    -- 对话次数
  MAX(h.create_time) AS last_chat_time          -- 最近对话时间
FROM sys_user u
LEFT JOIN wc_chat_history h ON u.user_id = h.user_id
WHERE h.create_time >= DATE_SUB(NOW(), INTERVAL 30 DAY)
GROUP BY u.user_id, u.nick_name
ORDER BY chat_count DESC;
```

### 3. 代码结构与模块划分（⭐⭐⭐ 必读）

#### 3.1 后端代码位置规范

**默认位置**：
```
FBSir-business/src/main/java/com/wx/fbsir/business/
├── controller/     # 控制器层
├── service/        # 服务层
├── domain/         # 实体类
├── mapper/         # 数据访问层
└── ...             # 其他业务代码
```

**重要规则**：
- ✅ **所有业务代码必须放在 `FBSir-business` 模块下**
- ✅ 按照功能模块划分子包（如 `content`、`agent`、`system` 等）
- ❌ **未经管理员允许，不得在其他模块存放业务代码**

#### 3.2 前端代码位置规范

**目录结构**（三级目录对应数据库菜单层级）：
```
FBSir-ui/src/
├── views/business/              # 业务页面根目录（对应一级菜单）
│   ├── content/                 # 内容管理（对应二级菜单）
│   │   ├── dailyassistant/      # 日更助手（对应三级菜单/具体页面）
│   │   │   ├── index.vue        # 页面主文件
│   │   │   └── components/      # 页面组件
│   │   ├── article/             # 文章管理
│   │   └── ...                  # 其他内容模块
│   ├── agent/                   # 智能体管理
│   └── ...                      # 其他业务模块
│
└── api/business/                # 业务API根目录
    ├── content/                 # 内容管理
    │   ├── dailyassistant.js    # 日更助手API
    │   ├── article.js           # 文章管理API
    │   └── ...                  # 其他API
    ├── agent/                   # 智能体API
    └── ...                      # 其他业务API
```

**重要规则**：
- ✅ **所有业务页面必须放在 `views/business/` 下的某个二级目录中**
- ✅ **所有业务API必须放在 `api/business/` 下的对应目录中**
- ✅ **目录层级必须与数据库菜单表层级对应**：
  - 一级目录：`business`（对应一级菜单）
  - 二级目录：功能模块（对应二级菜单，如 `content`、`agent`）
  - 三级目录：具体页面（对应三级菜单，如 `dailyassistant`）
- ✅ API文件名与页面目录名保持一致
- ❌ **未经管理员允许，不得在其他位置存放业务代码**

#### 3.3 为什么要严格遵守目录规范？

1. **模块独立**：各模块代码独立，便于维护和解耦
2. **权限对应**：目录层级与菜单权限一一对应，便于权限控制
3. **团队协作**：统一的目录结构降低沟通成本
4. **代码审查**：便于Code Review时快速定位代码位置

#### 3.4 特殊情况处理

如果你的功能确实不适合放在 `business` 目录下：
1. 先与管理员沟通说明原因
2. 获得批准后在PR中注明
3. 更新相关文档说明特殊目录的用途

### 5. 日志处理规范

#### 5.1 日志级别使用

**日志级别定义：**

| 级别 | 用途 | 使用场景 | 生产环境 |
|---|---|---|---|
| **ERROR** | 业务异常、系统错误 | 微信API调用失败、数据库操作失败、加密解密失败 | ✅ 输出 |
| **WARN** | 可恢复的异常状态 | 参数校验失败、资源不存在、配置缺失 | ✅ 输出 |
| **INFO** | 关键业务节点 | 文章创建成功、任务提交成功、重要状态变更 | ✅ 输出 |
| **DEBUG** | 详细调试信息 | HTTP请求详情、参数值、中间处理结果 | ❌ 不输出 |
| **TRACE** | 完整数据dump | 请求体完整内容、响应体完整内容 | ❌ 不输出 |

**开发环境配置：**
```yaml
# application.yml - 开发环境
logging:
  level:
    com.wx.fbsir: DEBUG              # 业务代码使用DEBUG，方便调试
    com.wx.fbsir.common.utils: DEBUG # 工具类使用DEBUG
    org.springframework: INFO         # Spring框架INFO
```

**生产环境配置：**
```yaml
# application.yml - 生产环境
logging:
  level:
    com.wx.fbsir: INFO               # 业务代码使用INFO，减少日志量
    com.wx.fbsir.common.utils: WARN  # 工具类只记录警告和错误
    org.springframework: WARN        # Spring框架只记录警告
    org.apache: ERROR                # Apache组件只记录错误
```

#### 5.4 特殊场景日志规范

**场景1：循环重试（只记录最终结果）**
```java
// ✅ 正确：单次失败不记录，全部失败才记录
public static String getPublicIp() {
    for (String url : IP_CHECK_URLS) {
        try {
            String ip = getIpFromUrl(url);
            if (ip != null && !ip.isEmpty()) {

        }

#### 5.5 日志规范总结

**必须遵守：**
- ✅ 所有异常必须记录日志
- ✅ 关键业务节点使用INFO
- ✅ 详细调试信息使用DEBUG
- ✅ 异常日志必须包含：错误类型、错误信息、业务上下文
- ✅ 使用业务标签：`[微信API]`、`[草稿箱]`、`[排版]`、`[AES加密]`

**禁止行为：**
- ❌ 禁止忽略异常不记录日志
- ❌ 禁止在INFO级别输出大量调试日志
- ❌ 禁止无意义的日志（如："进入方法"、"退出方法"）
- ❌ 禁止在日志中输出敏感信息（密钥、密码、Token）

**加密示例：**
```java
import com.wx.fbsir.common.utils.AesEncryptUtils;

// 保存时加密
String plainAppId = "wx1234567890abcdef";
String encryptedAppId = AesEncryptUtils.encrypt(plainAppId);
wcOfficeAccount.setAppId(encryptedAppId);
```

**解密示例：**
```java
// 使用时解密
String encryptedAppId = account.getAppId();
String plainAppId = AesEncryptUtils.decrypt(encryptedAppId);
```

**生成新密钥：**
```java
// 生成随机密钥（用于初始化或更换密钥）
String newKey = AesEncryptUtils.generateRandomKey();
System.out.println("新密钥: " + newKey);
```

#### 7.3 密钥配置

在 `application.yml` 中配置AES密钥：
```yaml
aes:
  secret:
    key: 你的64位复杂密钥
```

**密钥要求：**
- 长度：建议64个字符
- 包含：大小写字母、数字、特殊符号
- 复杂度：高度随机，无规律

#### 7.4 安全建议

**必须遵守：**
- ✅ 生产环境使用环境变量存储密钥
- ✅ 定期更换密钥（建议每3-6个月）
- ✅ 不同环境使用不同密钥
- ✅ 密钥不要提交到版本控制系统

**禁止行为：**
- ❌ 禁止在日志中输出密钥
- ❌ 禁止在前端代码中暴露密钥
- ❌ 禁止使用简单或规律的密钥（如：123456、password）
- ❌ 禁止将密钥硬编码在代码中

## 🔐 权限控制规范

### 权限设计与实现

**⚠️ 重要：所有页面功能必须使用若依的权限控制，特别是按钮级权限控制。**

### 核心要求

1. **前端权限控制**
   - ✅ 所有按钮必须使用 `v-hasPermi` 指令
   - ✅ 菜单权限通过路由配置的 `perms` 字段控制
   - ✅ 页面组件放在 `FBSir-ui/src/views/business/` 目录下
   - ✅ API 文件放在 `FBSir-ui/src/api/business/` 目录下

2. **后端权限控制**
   - ✅ 所有 Controller 接口必须添加 `@PreAuthorize` 注解
   - ✅ 业务代码放在 `FBSir-business/src/main/java/com/wx/fbsir/business/` 包下
   - ✅ 数据查询必须过滤 userId，确保数据隔离
   - ✅ 删除/修改操作必须验证数据所有权

3. **数据库权限配置**
   - ✅ 菜单ID规划：一级(1-99)、二级(100-499)、三级(500-999)、按钮(1000+)
   - ✅ 业务二级菜单从 117 开始
   - ✅ 业务按钮权限从 1061 开始
   - ✅ 权限标识格式：`模块:功能:操作`（如：`business:daily:add`）

### 示例代码

**前端按钮权限：**
```vue
<el-button
  type="primary"
  icon="Plus"
  @click="handleAdd"
  v-hasPermi="['business:daily:add']"
>
  新增文章
</el-button>
```

**后端接口权限：**
```java
@PreAuthorize("@ss.hasPermi('business:daily:add')")
@PostMapping
public AjaxResult add(@RequestBody DailyArticle dailyArticle) {
    dailyArticle.setUserId(getUserId());
    return toAjax(dailyArticleService.insertDailyArticle(dailyArticle));
}
```
