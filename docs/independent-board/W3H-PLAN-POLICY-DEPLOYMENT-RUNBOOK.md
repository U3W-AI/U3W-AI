# 独董会 W3h 套餐策略治理部署准备手册

状态：本地候选已实现，生产迁移、菜单授权、HTTP 开关和前端开关均未启用。

本手册只覆盖 `admin.u3w.com` 的套餐策略治理候选能力。归因继续处于次要优先级；已提交审核并冻结的独董会 `26.7.20` 包不参与本次发布，也不得被回写。

## 1. 变更边界

- 公共数据库步骤：`public_init_039`，文件为 `sql/update_20260722_independent_board_plan_policy.sql`。
- 候选权限迁移：`sql/update_20260722_independent_board_plan_policy_candidate_menu.sql`，必须显式设置会话变量 `@u3w_enable_independent_board_w3h_plan_policy_candidate = 1`；迁移只创建两个默认禁用、零角色绑定的功能身份。
- 后端开关：`FBSIR_INDEPENDENT_BOARD_PLAN_POLICY_CANDIDATE_ENABLED`，默认 `false`。
- 前端构建开关：`VITE_FBSIR_BOARD_PLAN_POLICY_CANDIDATE`，只有严格等于字符串 `true` 才展示治理面板。
- 细粒度权限：`board:plan:revise`、`board:plan:audit`；后端还要求全局 `admin` 角色。
- 生产权威仍是数据库中已提交的策略 head 与不可变回执。浏览器草稿、网络超时和界面提示都不是提交事实。

4. 数据库 manifest、W3h 双版本矩阵、候选菜单矩阵、后端定向回归、前端验证器和生产构建均通过当前提交。

## 3. 分波实施

### 波次 A：离线预置关闭态工件，不切生产流量

1. 预置后端工件和前端关闭态构建，但后端工件不得接收生产流量；前端保持 `VITE_FBSIR_BOARD_PLAN_POLICY_CANDIDATE=false`。
2. 在等效环境确认后端默认 `FBSIR_INDEPENDENT_BOARD_PLAN_POLICY_CANDIDATE_ENABLED=false`，新写入与审计路径为关闭态语义并带 `Cache-Control: no-store`。
3. 记录待切换的全部读写实例、定时任务和旁路写入，禁止遗漏仍可写入 `fbs_usage_operation` 的旧代码。
4. 不允许在 `public_init_039` 前把本轮后端代码切入生产；既有套餐、权益和会议路径已无条件依赖 039 新表，关闭候选控制器并不能隔离这些依赖。

### 波次 B：维护窗口内原子完成停写、迁移与整组后端切换

1. 再次确认所有独董会写入已排空；维护窗口内不得恢复旧后端会议写入。
2. 使用仓库标准初始化器执行到 `public_init_039`，禁止复制 SQL 片段手工执行。
3. 立即运行初始化器的只读当前态验证，确认三张表、两条 baseline、两条 head、全部历史 operation 血缘、原始元数据摘要和触发器正文完全一致。
4. 失败时不要重建或删除目标表；保留失败回执和日志，按初始化器的有界恢复语义处理。
5. 迁移验证成功后，在仍保持停写的前提下升级并切换全部可写后端实例；所有实例均保持候选 HTTP 开关关闭。
6. 先通过隔离探针验证既有套餐只读、权益、会议、连接器和 OAuth 路径，再恢复只读流量；确认没有旧写实例后才恢复会议写流量。
7. 如果新后端切换失败，继续停写并回到维护决策点；不得让旧后端在已完成 039 的数据库上生成没有策略血缘的新 operation。

### 波次 C：安装默认禁用权限身份

1. 在独立审计会话中显式设置 `@u3w_enable_independent_board_w3h_plan_policy_candidate = 1`，执行候选菜单迁移。
2. 确认恰好存在 `board:plan:revise`、`board:plan:audit` 两个功能身份，均为禁用态，且角色绑定数为零。
3. 不得手工新增路由、页面菜单或默认角色绑定。

### 波次 D：单实例、单操作者候选验证

1. 先只在一个管理后台实例启用后端开关，并使用前端候选构建；其他实例继续关闭。
2. 首个操作者只使用内置全局超级管理员。普通管理员授权必须另有经审计的角色绑定变更。
3. 先验证两套餐当前读与最多 100 条审计回执，再执行一笔已批准的完整修订。
4. 对同一请求使用原负载与原幂等键精确重放，必须返回同一回执且不增加版本。
5. 验证陈旧版本返回稳定 `409`，界面保留旧表单、旧预期版本和原幂等键，不自动套用新版本。
6. 如需恢复业务值，只能发起生成 `N+1` 的补偿回滚；禁止更新、删除历史回执或让 head 指回旧版本。

### 波次 E：扩大范围

只有在候选窗口中确认无异常写入、无未知 `5xx`、回执链连续、会议 operation 都绑定策略回执后，才可逐实例扩大。每次扩大都要记录实例、构建提交、开关值、操作者、首尾时间和回读结果。

## 4. 回退策略

- 应用级快速回退：先将后端开关恢复为 `false`，再部署前端关闭态构建；关闭或解绑两个候选权限身份。
- 数据库不得做“反向迁移”：三张新表、baseline、head、operation 血缘和不可变回执保留，避免审计链断裂。
- 业务策略回退使用受控补偿命令创建新版本，不使用 SQL 改写当前 head。
- `public_init_039` 完成后，旧后端不具备为新 meeting operation 同事务写入策略血缘的能力，绝不能恢复为写实例。若必须恢复上线前状态，只能在持续停写下把数据库备份与全部应用实例一起恢复到同一窗口前精确版本；不得把“仅回退应用”视为安全回退。
- 只有数据库灾难恢复场景才使用上线前备份；恢复后必须重新对齐应用提交、manifest 回执和迁移窗口内业务数据，不能把备份恢复等同于正常回滚。
